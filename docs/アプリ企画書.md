# Gitぱっち

## どんなアプリか

Gitぱっちは、Gitを使い始めた学生のための、ペット育成つきGit活動記録CLIアプリです。

課題を少し進めてコミットしても、「今日はちゃんと開発できた」と感じる機会は意外と少ないと思います。そこで、リポジトリの最新コミットを確認するとペットが経験値を獲得して成長する仕組みにしました。Gitを使うことそのものを少し楽しくし、コミットを続けるきっかけを作ることが目標です。

## 解決したいこと

Gitを始めたばかりのときは、コミットの意味や習慣化する良さを実感しにくいです。コマンドを覚えるだけでは、毎日の小さな作業が続かないこともあります。

Gitぱっちでは、Git活動を「ペットの成長」という分かりやすい結果に変えます。利用者がリポジトリを登録し、最新コミットを確認すると、ペットに経験値が入ります。なでる・ごはんをあげる操作も用意し、作業の合間に気軽に開けるアプリを目指します。

## 想定する利用者

**竜樹諒さん（19歳・情報系専門学生）**

- 授業でGitを使い始めたばかり
- コミットを忘れたり、開発が止まりがち
- 難しいGit操作より、まずは結果が分かりやすい画面を求めている
- 課題制作のあとに、自分のGit活動をすぐ確認したい

## 利用の流れ

1. 利用者がローカルのGitリポジトリを登録する。
2. アプリでリポジトリの最新コミットを確認する。
3. 前回確認したコミットより新しければ、ペットに経験値を与える。
4. 利用者はペットのレベル・経験値・満腹度・機嫌を確認する。
5. アプリを終了しても、ペットと登録リポジトリの情報はCSVに保存される。

同じコミットを何度確認しても経験値が増えないようにし、「実際に新しくコミットしたこと」が成長につながるようにする。

## MVPで作る機能

| 機能 | できること |
| --- | --- |
| リポジトリ登録 | 表示名とローカルパスを登録する |
| リポジトリ管理 | 一覧表示・編集・削除をする |
| Git活動確認 | 最新コミットIDを取得し、新しいコミットなら経験値を与える |
| ペット表示 | 名前、レベル、経験値、満腹度、機嫌を表示する |
| お世話 | なでる・ごはんをあげて、ペットの状態を変える |
| CSV保存 | 終了後もペットと登録リポジトリを復元する |

## 今回は作らないもの

最初から機能を増やしすぎないため、以下はMVPの外に置く。

- GitHub CLI連携、push回数の集計
- ショップ、進化、複数ペット、ミニゲーム
- アイテムの購入・所持品管理
- JSON・データベース保存
- リポジトリ検索・並び替え・アニメーション

これらは、基本の「登録 → Git活動確認 → ペット成長」が安定して動いてから検討する。

## データ設計

| クラス | 主に持つ情報 | 考え方 |
| --- | --- | --- |
| `Pet` | 名前、レベル、経験値、満腹度、機嫌 | ペット自身の現在の状態 |
| `RepositoryProfile` | 表示名、パス、最後に確認したコミットID | 登録したGitリポジトリ1件の状態 |
| `Item` | 名前、価格、効果 | 将来のショップ用。MVPでは使わない |
| `InventoryItem` | アイテム、所持数 | 将来の所持品用。MVPでは使わない |

最後に確認したコミットIDは、ペットではなく `RepositoryProfile` に持たせる。複数のリポジトリを登録したとき、それぞれで「どこまで経験値を与えたか」を判断できるためである。

## クラスの役割

| クラス | 種類 | 役割 |
| --- | --- | --- |
| `Main` | 起動 | 必要なオブジェクトを作り、アプリを開始する |
| `Menu` | UI | メニュー表示、入力受付、結果表示を行う |
| `Pet` | モデル | ペットの状態を保持する |
| `RepositoryProfile` | モデル | 登録リポジトリ1件の情報を保持する |
| `PetService` | サービス | 経験値、レベルアップ、お世話のルールを処理する |
| `RepositoryService` | サービス | リポジトリの登録・一覧・編集・削除を行う |
| `GitActivityService` | サービス | Gitコマンドで最新コミットを取得する |
| `CsvStorage` | 保存 | ペットとリポジトリ情報をCSVへ保存・復元する |
| `Item` / `InventoryItem` | モデル | 将来機能用。MVPでは使用しない |

`Main` にすべての処理を書くのではなく、入力は `Menu`、状態はモデル、処理はService、保存は `CsvStorage` に分ける。この分け方にしておくと、Gitコマンドの失敗時の案内やCSV保存の修正を、ほかの処理に影響させずに行いやすい。

## エラー時に大切にすること

初心者向けのアプリなので、失敗したときに専門用語だけで終わらせない。

- パスが存在しない：登録内容を確認するよう伝える
- Gitリポジトリではない：`git init` 済みのフォルダを選ぶよう伝える
- コミットがない：最初のコミット後にもう一度確認するよう伝える
- 数字以外のメニュー入力：番号を入力するよう伝える
- CSVが壊れている：原因を表示し、アプリ全体は終了させない

## 完成したと判断する基準

利用者が、説明を受けなくても「リポジトリを登録する → Git活動を確認する → ペットが成長する」までを進められることを完成の基準にする。さらに、アプリを再起動しても情報が残り、不正な入力やGit確認の失敗で突然終了しない状態を目指す。

## レビューで見てほしいこと

1. 初心者が中心の流れを迷わず操作できるか。
2. リポジトリCRUDとペット育成の責務が混ざっていないか。
3. GitコマンドやCSVの失敗を、利用者が次の行動を選べる形で案内できているか。
4. MVPの範囲が、課題として最後まで完成させられる大きさになっているか。
