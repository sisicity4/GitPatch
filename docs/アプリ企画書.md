# Gitぱっち

## どんなアプリか

Gitぱっちは、Gitを使い始めた学生のための、ペット育成つきGit活動記録CLIアプリです。

課題を少し進めてコミットしても、「今日はちゃんと開発できた」と感じる機会は意外と少ないと思います。そこで、リポジトリの最新コミットを確認するとペットが経験値を獲得して成長する仕組みにしました。Gitを使うことそのものを少し楽しくし、コミットを続けるきっかけを作ることが目標です。

## 解決したいこと

Gitを始めたばかりのときは、コミットの意味や習慣化する良さを実感しにくいです。コマンドを覚えるだけでは、毎日の小さな作業が続かないこともあります。

Gitぱっちでは、Git活動を「ペットの成長」という分かりやすい結果に変えます。利用者がリポジトリを登録し、最新コミットを確認すると、ペットに経験値が入ります。なでる・ごはんをあげる操作も用意し、作業の合間に気軽に開けるアプリを目指します。

## 想定する利用者

**竜樹諒さん（19歳・情報系専門学生）**

- 授業でGitを使い始めたばかり
- コミットを忘れたり、開発が止まりがち
- 難しいGit操作より、まずは結果が分かりやすい画面を求めている
- 課題制作のあとに、自分のGit活動をすぐ確認したい

## 利用の流れ（現在の実装）

1. 利用者がローカルのGitリポジトリを登録する。
2. 確認対象のリポジトリを一覧から選ぶ。
3. Git活動を確認し、最新コミットIDを取得する。
4. 前回確認したコミットIDと異なれば、その場でペットに経験値30を与え、`lastCheckedCommitId` を更新する。
5. 利用者はペットのレベル・経験値・満腹度・機嫌を確認する。

同じコミットを連続して確認した場合は経験値が増えない。現在は最新1件と直前の `lastCheckedCommitId` だけを比較しているため、過去に報酬を与えたコミットが再び最新になった場合の重複防止は未実装である。状態はメモリ上でのみ保持するため、終了するとペットと登録リポジトリの情報は失われる。CSV保存は未実装である。

### リポジトリ発見の次段階仕様

現在は利用者がローカルのGitリポジトリのパスを入力する。次の段階では、利用者が検索対象のフォルダを登録し、その配下にあるclone済みのGitリポジトリを探せるようにする。

- 検索対象は利用者が追加したフォルダの配下だけとし、PC全体やルートからは検索しない。
- `.git` ディレクトリ、またはworktreeで使われる `.git` ファイルがあるフォルダをGitリポジトリ候補とする。
- 候補からremote URLを取得し、GitHub URLと一致するcloneを選べるようにする。
- 同じリポジトリのcloneが複数見つかった場合は、パスを表示して利用者が選択する。
- 権限がないフォルダは全体を失敗させず、スキップして結果を案内する。
- 見つかったフォルダは既存のローカルGit確認処理で利用する。GitHub APIによる直接確認や自動cloneは、この段階では必須にしない。

この機能はMVP完成後の発展機能とし、まずは検索フォルダを限定した安全な検索を実装する。

### `feature/activity-streak` ブランチの現在地

このブランチでは、連続記録の基礎ロジックを先行して実装している。`ActivityStreak` が `currentStreak`、`longestStreak`、`lastActivityDate` を保持し、`ActivityStreakService` が初回・同日・翌日・空白日・最長記録・過去日の判定を行う。`MainTest` でこれらの基礎ケースを確認済みである。

現在は `Main` から `Menu` へ連続記録を渡し、新しいGit活動の確認時に更新している。`MainTest` では初回・同日・翌日・空白日・最長記録・過去日の確認に加え、3/7/14日の称号境界とMenuのGit活動確認経路を確認している。`Menu.start` 全体の自動統合テストと保存は未完了である。

## 新仕様の企画（活動同期と連続記録）

現行実装の「確認した時点で即時に報酬を確定する」方式を、CLIに合わせて次の方式へ整理する。CLIではコミットが作られた瞬間を常時監視できないため、**コミットの発生時ではなく、次回の活動同期で報酬を確定する**。`feature/activity-streak` では、まずこの活動日を受け取る連続記録の基礎判定を実装している。

- 活動同期では、前回同期以降のコミットを確認し、報酬の対象を確定する。
- 同じコミットを再確認した場合は **0XP** とする。
- 同じ日に別のコミットを確認した場合は、通常どおり **30XP** を付与する。
- 前回の活動日が前日なら `currentStreak` を1増やす。
- 活動日の間に空白日があれば `currentStreak` をリセットする。
- 最初の活動日は `currentStreak` を1とし、最大値を `longestStreak` に記録する。
- 活動日を `lastActivityDate` に記録する。判定はPCのローカル時刻の日付単位で行う。
- 連続3日で「Git見習い」、7日で「Gitマン」、14日で「Gitスター」を付与する。
- 連続が切れたら「今日はGitさわれなかったのかな? また1から頑張ろう！」と表示する。
- 同じ日に複数リポジトリで活動しても、各新規コミットを通常どおり30XPへ変換する。streakはその日1回だけ増える。
- 連続記録保護は今回の実装に含めない。

最初から複雑な倍率や報酬表は導入せず、XPはまず30固定とする。`currentStreak`、`longestStreak`、`lastActivityDate` の永続化はCSV保存を実装した後に行う。現時点では、連続記録の基礎判定、活動同期への接続、称号、節目・記録切れメッセージ、CLI表示まで実装済みで、CSV保存は未完了である。

## 新仕様の実装段階

実装済みのMVPと仕様案を混同しないため、段階を次のように分ける。

- **実装済み**：リポジトリ登録、一覧、編集、削除、選択、Git活動確認、異なるコミットへの固定30XP、`lastCheckedCommitId` 更新。
- **ブランチ内で基礎実装済み**：`ActivityStreak` による日付単位の `currentStreak` / `longestStreak` / `lastActivityDate` の更新。`MainTest` で初回・同日・翌日・空白日・最長記録・過去日のケースを確認済み。
- **実装済み**：streakの数値・称号・節目メッセージのCLI表示、1日の活動目標。連続記録保護は今回の実装対象外。
- **未実装**：CSV保存・復元、連続記録の永続化。全角数字の自動テストも未実装である。
- **未テスト**：`Menu.start` の対話操作全体を通した統合テスト。Git活動確認の主要経路は`MainTest`で確認済み。
- **次段階の仕様案**：検索フォルダの登録、配下の`.git`を持つclone候補の検索、remote URLによる候補の絞り込み。まだ未実装である。

## 今回は作らないもの

最初から機能を増やしすぎないため、以下はMVPの外に置く。

- GitHub CLI連携、push回数の集計
- ショップ、進化、複数ペット、ミニゲーム
- アイテムの購入・所持品管理
- JSON・データベース保存
- GitHub URLからの直接API確認、自動clone、リポジトリの並び替え・アニメーション

検索フォルダから既存cloneを探す機能は、基本の「登録 → Git活動確認 → ペット成長」が安定してから、次段階として検討する。

## データ設計

| クラス              | 主に持つ情報                                   | 考え方                                                                                   |
| ------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `Pet`               | 固定名「ぱっち」、レベル、経験値、満腹度、機嫌 | ペット自身の現在の状態                                                                   |
| `RepositoryProfile` | `repoName`、パス、最後に確認したコミットID     | 登録したGitリポジトリ1件の状態。将来は`remoteUrl`を追加し、検索で見つけたcloneとの対応を保持する案がある |
| `Item`              | 現在は情報を持たない空クラス                   | 将来のショップ用。MVPでは使わない                                                        |
| `InventoryItem`     | 現在は情報を持たない空クラス                   | 将来の所持品用。MVPでは使わない                                                          |

ペット名はMVPでは固定の「ぱっち」とし、利用者による名前変更は扱わない。最後に確認したコミットIDは、ペットではなく `RepositoryProfile` に持たせる。複数のリポジトリを登録したとき、それぞれで「どこまで経験値を与えたか」を判断できるためである。

## クラスの役割

| クラス                   | 種類         | 役割                                                                                                                      |
| ------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `Main`                   | 起動         | 必要なオブジェクトを作り、アプリを開始する                                                                                |
| `Menu`                   | UI           | メニュー表示、入力受付、結果表示を行う                                                                                    |
| `Pet`                    | モデル       | ペットの状態を保持する                                                                                                    |
| `RepositoryProfile`      | モデル       | `repoName`、パス、最後に確認したコミットIDを保持する                                                                      |
| `PetService`             | サービス     | 経験値、レベルアップ、お世話のルールを処理する                                                                            |
| `RepositoryService`      | サービス     | リポジトリの登録・一覧・編集・削除を行い、`RepositoryStatus` で成功・失敗理由を返す。Menuのリポジトリ管理から利用する |
| `GitActivityService`     | サービス     | Git状態を `GitStatus` enumで判定し、最新コミットIDを取得・比較する                                                        |
| `ActivityStreak`         | モデル       | 連続日数、最長記録、最後の活動日をメモリ上で保持する                                                                      |
| `ActivityStreakService`  | サービス     | 活動日を比較し、連続記録と最長記録を更新する。`Menu` のGit活動確認から呼び出す                                         |
| `CsvStorage`             | 保存（予定） | 現在は空クラス。CSV保存・復元と連続記録の永続化は未実装                                                                   |
| `Item` / `InventoryItem` | モデル       | 将来機能用。MVPでは使用しない                                                                                             |

`Main` にすべての処理を書くのではなく、入力は `Menu`、状態はモデル、処理はService、保存は `CsvStorage` に分ける。この分け方にしておくと、Gitコマンドの失敗時の案内やCSV保存の修正を、ほかの処理に影響させずに行いやすい。

## エラー時に大切にすること

初心者向けのアプリなので、失敗したときに専門用語だけで終わらせない。

- パスが存在しない：登録内容を確認するよう伝える
- Gitリポジトリではない：`GitStatus.NOT_GIT_REPOSITORY` を受け、`git init` 済みのフォルダを選ぶよう伝える
- コミットがない：`GitStatus.NO_COMMIT` を受け、最初のコミット後にもう一度確認するよう伝える
- 数字以外のメニュー入力：番号を入力するよう伝える
- 検索フォルダを読めない：権限を確認するか、別の検索フォルダを指定するよう伝える（検索機能の実装時）
- CSVが壊れている：CSV保存・復元の実装時に、原因を表示し、アプリ全体は終了させない（現在は未実装）

## 完成したと判断する基準

現在の到達点は、利用者が「リポジトリを登録する → 管理メニューで一覧・編集・削除する → 確認対象を選ぶ → Git活動を確認する → 新規コミットならその場でペットが成長する」までをCLIで進められる状態である。`feature/activity-streak` では連続記録の基礎判定まで進んでいる。不正なメニュー入力、リポジトリ選択、Git確認の代表的な失敗はメッセージで案内する。お世話の回復量は種類ごとの固定値である。

完成基準として残っているのは、CSVによる保存・復元、空のGitリポジトリを `NO_COMMIT` として適切に案内できること、およびGit活動以外も含む操作フローの全体テストである。検索フォルダからcloneを探す機能は、その後の発展課題である。

## レビューで見てほしいこと

1. 初心者が中心の流れを迷わず操作できるか。
2. リポジトリCRUDとペット育成の責務が混ざっていないか。
3. GitコマンドやCSVの失敗を、利用者が次の行動を選べる形で案内できているか。
4. MVPの範囲が、課題として最後まで完成させられる大きさになっているか。
